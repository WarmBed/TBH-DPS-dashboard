# 通關提速模擬 — 可行性與資料缺口分析

- 日期：2026-06-26
- 狀態：**可行性分析，尚未成為 spec**（使用者選擇「先只要分析、暫不寫功能」）
- 問題：對每一關，「我提升 DPS / 提升速度，分別能加速多少通關時間？」例如裝某件道具提升了某角色的速度或 DPS，能不能換算成省幾秒？

---

## 0. TL;DR

- 你想問的兩件事拆開來是：**提輸出能壓多少時間**、**提移動能壓多少時間**。
- **好消息：核心引擎已經存在。** 插件已經把通關時間拆成「輸出時間」和「跑路時間」兩段——這正是你問題的答案來源。
- **不用每關重打。** 只要打過幾關（涵蓋不同波數/HP），模型就能外推到全部 108 關。只有「換裝備」才需要重新校準，而換裝偵測已經自動化。
- 真正難、且我建議**避開純預測**的是層級 3「裝這件裝備自動算省幾秒」——那需要遊戲傷害公式，會被改版打爛。

## 1. 為什麼通關時間可以被拆開

通關時間本質上由兩種完全不同的瓶頸組成：

```
通關秒數  =  輸出時間 (打怪)        +  跑路時間 (移動/生怪/換波)
             └ 只跟「DPS」有關         └ 只跟「移動速度」有關
             └ DPS×2 → 這段 ÷2        └ 速度×2 → 這段大致 ÷2(見第5節)
```

提 DPS 只會壓縮「輸出時間」那一段，對「跑路時間」毫無幫助；提速度反過來。
**這就是為什麼「裝攻擊裝」和「裝速度裝」對不同關卡的效果天差地遠**——一關如果 90% 時間在打怪，
就該堆攻擊；另一關如果一半時間在跑路，堆速度才划算。

插件裡這個拆分有**兩個現成來源**：

1. **跨關回歸模型**（`FarmPlanner.cs`）：
   `通關秒數 ≈ PerWaveSec × 波數 + SecPerHP × 總HP`
   - `SecPerHP` = 1 / 有效DPS（每點HP要花幾秒 → 輸出瓶頸）
   - `PerWaveSec` = 每波固定開銷（生怪/換波 → 跑路瓶頸）
   - 用「至少 2 場、波數/HP 不同」的 run 做最小平方擬合，然後**外推到所有 108 關**。

2. **單場直接量測**（`OverlayBehaviour.cs` → `RunRecord`）：
   - `ActiveSeconds` = 那一場「正在輸出」的時間
   - `IdleSeconds` = 那一場「沒輸出 = 在跑路」的時間

設計上兩者互補：**已打過的關**用它自己的 Active/Idle（真實量測），**沒打過的關**用回歸模型外推。

## 2. 現有資料盤點（這些都已經有了）

| 資料 | 來源 | 用途 |
|---|---|---|
| 每波/總時長、波數 | `RunRecord.Duration / WaveDurations / Waves` | 時間基準 |
| **輸出時間 / 跑路時間** | `RunRecord.ActiveSeconds / IdleSeconds`（`OverlayBehaviour.cs:148`） | **DPS↔速度 拆分的核心** |
| 全隊有效DPS | `RunRecord.Total / Duration`、`Peak`、`Avg` | 模擬基準 |
| 兩段時間模型參數 | `Calibration.PerWaveSec / SecPerHP`（`FarmPlanner.cs:330`） | 外推未打關卡 |
| 每關靜態 HP/波數/獎勵 | `farm_stages.json`（108 關）+ wiki | 外推目標 |
| 換裝偵測指紋 | `FarmPlanner.BuildSignature`（裝備+詞綴，刻意忽略等級/技能等級） | 自動判定資料是否過期 |
| 每角色 DPS 佔比 | F9 詳細 `Snapshot.ByChar`（live） | 層級 2 需要，但**目前沒存進 run 檔** |

## 3. 三個層級的資料缺口

### 層級 1：敏感度模擬 — 缺的資料：**零**
- 給兩條滑桿：`DPS ×k₁`、`速度 ×k₂`。
- 重算每關：`新時間 = 輸出時間/k₁ + 跑路時間/k₂`（已打關用 Active/Idle；未打關用 `SecPerHP·HP/k₁ + PerWaveSec·波數/k₂`）。
- 每關標一個徽章：`輸出時間 ÷ 總時間` → 「吃 DPS 85%」vs「吃速度 70%」。
- **資料全部現成，馬上能做、最穩。** 直接回答你「提速能省多少」的核心問題。

### 層級 2：指定某個角色 — 缺的資料：**per-char DPS 佔比的持久化**
- 「把法師拉 20%」要先知道法師佔全隊輸出幾 %：
  - 法師佔 0.4% → 拉他 2 倍，全隊 DPS 幾乎不動 → 通關沒變快（呼應你「法師範圍攻擊」的直覺：要看他實際貢獻）。
  - 法師佔 60% → 拉 20%，全隊約 +12% → 套進層級 1 算省時。
- F9 詳細模式**已經會算** `ByChar` 佔比，但只存在記憶體、**沒寫進 `RunRecord`**。
- **怎麼拿**：在 run 凍結時把 `Snapshot.ByChar` 的每角色 total/share 一起序列化進 run 檔。一次小改，不用重打任何關。

### 層級 3：裝這件裝備 → 自動算省幾秒 — 缺的資料：**遊戲傷害公式（最脆）**
- 要把「裝備詞綴（攻擊%/暴擊/攻速）」翻譯成「有效 DPS 提升 %」。
- **為什麼危險**：
  1. 需要逆向遊戲傷害公式，而你踩過 IL2CPP 改版地獄（`tbh-game-update` runbook 就是在收拾這種爛攤）。每次改版都可能整組失效。
  2. **法師 AoE / 溢傷**讓「單體攻擊 +X%」≠「清關速度 +X%」。量到的 DPS 其實**已經含 AoE**（打到每隻怪的傷害都算），但若該關怪很稀疏、AoE 打空，加單體攻擊也救不回來。
- **替代方案（建議）**：層級 3 不要做純預測，改用
  - **A/B 實測**：戴上裝備打一場、脫掉打一場，直接比 measured DPS（`BuildSignature` 會自動把兩種建構分開）；或
  - **手動滑桿**：你自己估「這件大概 +X% 攻擊」，丟進層級 1 算。

---

## 4. 「每一關都要再通關一次嗎？」→ **不用**

- **擬合模型**只需要幾關（不同波數/HP 各 1 場）就能 fit 出 `PerWaveSec / SecPerHP`，然後外推到全部 108 關。
- **只有換裝備**才需要重新校準。而 `FarmPlanner.BuildSignature` 已經自動偵測換裝：
  - 換/洗裝 → 指紋改變 → 舊 run 自動標記「過期」，不再參與校準。
  - 升等 / 升技能等級**刻意不算**換建構（正常遊玩會慢慢漲，不該重設基準；等級另由 exp-retention 模型處理）。
- 所以實務上：固定一套裝備打幾關 → 全圖可模擬；之後只在換裝後補打少數幾關即可。

---

## 5. 必須誠實面對的誤差來源（模擬是「方向準」，不是碼錶準）

1. **溢傷 overkill**：怪剩 1 滴血卻吃了一發大招，多出的傷害灌水 measured DPS，但不會讓關卡更快。
2. **AoE**：measured DPS 已含 AoE 收益，但「加單體攻擊」未必等比例轉成清關速度。
3. **攻速 breakpoint / 動畫**：DPS 不是連續線性，可能卡施法動畫，+10% 攻擊未必 = +10% 實際輸出。
4. **`IdleSeconds` 不全是「移動」**：也含生怪等待、換波動畫等「速度救不了」的固定開銷——所以「提速度」的上限被這部分吃掉。
5. **遠階外推**：`FarmPlanner` 不建模「怪物護甲隨等級成長」，純線性外推——越遠的高階關誤差越大（這是現有限制，沿用）。

> 結論：當「相對比較器」（哪關吃 DPS、哪關吃速度、哪個投資報酬高）非常好用；當「精準碼錶」會失準。UI 上應呈現為「約省 X 秒 / Y%」並標註是估計。

---

## 6. 建議順序

1. **先做層級 1（敏感度模擬）**——零新資料、最穩、直接回答你的核心問題。
2. **層級 2** 視 per-char 佔比持久化的成本再決定（小改）。
3. **層級 3 不要做純預測**，用 A/B 實測或手動滑桿替代。

### 用測試資料舉個具體例子
以 `TrackerTests` 裡的一場 run 為例：`ActiveSeconds = 61s`、`IdleSeconds = 11.8s`（總 ≈ 72.8s）。

- **DPS +20%**：輸出時間 61 ÷ 1.2 = 50.8s → 總 62.6s → **省 10.2s（約 14%）**
- **速度 +20%**：跑路時間 11.8 ÷ 1.2 = 9.8s → 總 70.8s → **省 2s（約 2.7%）**

→ 這關是**重輸出關**：堆攻擊的報酬是堆速度的 5 倍。換一關（跑路占比高的）結論可能完全相反——
而這正是這個功能的價值：**幫你針對每一關決定該堆攻擊還是堆速度。**
